Server side

1. REST – Principi fondamentali

REST è uno stile architetturale per API basate su HTTP.

  • Stateless: ogni richiesta contiene tutte le info necessarie, il server non ricorda le richieste precedenti.
  • Basato su risorse: URI come /users, /users/10.
  • Metodi HTTP usati come CRUD (GET, POST, PUT, PATCH, DELETE).
  • Rappresentazioni tipiche: JSON, XML, HTML.
Metodo Azione Idempotente Side effects Uso tipico
GET Lettura Sì No Recuperare dati (safe)
POST Creazione No Sì Creare nuove risorse
PUT Sostituzione completa Sì Sì Aggiorna o crea intera risorsa
PATCH Modifica parziale Non sempre Sì Aggiorna campi specifici
DELETE Eliminazione Sì Sì Cancella risorsa

Idempotenza: N chiamate producono lo stesso risultato finale della prima.

  • GET /concerti/10 ×5 → solo lettura, nessuna modifica.
  • POST /biglietti ×5 con lo stesso body → 5 biglietti creati (side effects).
  • DELETE /biglietti/7 ripetuto → prima 204, poi 404 o ancora 204 (idempotente).
GET: safe & idempotente POST: non idempotente

1.2 Nesting di risorse

Rappresenta relazioni gerarchiche parent → child.

Esempi

/artisti/3/concerti – concerti dell’artista 3
/artisti/3/concerti/12 – concerto 12 dell’artista 3
/corsi/5/prenotazioni – prenotazioni corso 5

Regole

  • Usare nesting se c’è parent-child chiaro.
  • Il parent deve esistere per accedere al child.
  • Evitare più di 2–3 livelli.

1.3 PUT vs POST per creazione

POST /corsi

URI di collezione, server genera l’ID.

POST /corsi Body: {"nome": "Yoga", "orario": "10:00"} → 201 Created, Location: /corsi/23

PUT /corsi/100

Client conosce l’URI completo.

PUT /corsi/100 Body: {"nome": "Yoga", "orario": "10:00"} → crea se non esiste, altrimenti sostituisce

POST: server decide l’URI (collezione). PUT: client decide l’URI della risorsa specifica.

1.4 Principio stateless

Il server non mantiene stato tra le richieste.

1) Client-side state

  • Carrello in memoria/localStorage.
  • Ad ogni richiesta il client manda tutti i dati necessari.
  • Alla conferma: POST /ordini con l’intero carrello.

2) Server-side con token

  • Server crea sessione/carrello con ID.
  • Client invia token/session ID in ogni richiesta.
  • Più vicino alle sessioni tradizionali, utile per multi-device.
  • Ogni richiesta deve essere auto-contenuta.
  • Autenticazione tipica: token/JWT a ogni chiamata.
  • Scalabilità: qualsiasi server può gestire qualsiasi richiesta.

2. HTTP status code

Classi principali: 2xx successo, 4xx errore client, 5xx errore server.

2xx – richiesta riuscita (OK, Created, No Content).
4xx – problema causato dal client (Bad Request, Unauthorized, Not Found, Conflict).
5xx – errore del server (Internal Server Error, Service Unavailable).
Codice Significato Quando usarlo
200 OK Successo con body GET, PATCH riusciti
201 Created Risorsa creata POST riuscito
204 No Content Successo senza body DELETE, PUT riusciti
400 Bad Request Richiesta malformata JSON invalido, parametri mancanti
401 Unauthorized Non autenticato Token mancante/scaduto
403 Forbidden Non autorizzato Autenticato ma senza permessi
404 Not Found Risorsa non trovata GET /concerti/999 inesistente
405 Method Not Allowed Metodo non permesso DELETE su risorsa non cancellabile
409 Conflict Conflitto con stato corrente Prenotare corso già completo
500 Internal Server Error Errore generico server Bug, crash
503 Service Unavailable Servizio non disponibile Database offline, manutenzione

Scenari tipici

  • GET /concerti/999 inesistente → 404 Not Found.
  • DB offline → 503 Service Unavailable.
  • POST concerto creato → 201 Created + Location /concerti/15.
  • PUT corso aggiornato → 200 OK (con body) o 204 No Content.
  • Corso già pieno → 409 Conflict.
fetch non fallisce su 404/500: controllare sempre response.ok

3. MIME Types & Content-Type

Indicano al server/cliente il tipo di contenuto del body.

MIME type Descrizione
application/json Dati JSON
text/html Documento HTML
text/plain Testo semplice
application/xml Dati XML
multipart/form-data Form con file
application/x-www-form-urlencoded Form standard

Esempio POST JSON

fetch(URL, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ name: "Mario" }) });
  • Il server deve sapere come parsare il body.
  • Senza Content-Type corretto, parsing può fallire.
  • Molti framework rispondono 400 Bad Request se il tipo non è coerente.

4. Semantic Versioning (SemVer)

Formato: MAJOR.MINOR.PATCH (es. 4.18.2).

PATCH (x.y.+1)

  • Bugfix e correzioni.
  • Retrocompatibile.

MINOR (x.+1.0)

  • Nuove feature.
  • Retrocompatibile.

MAJOR (+1.0.0)

  • Breaking changes.
  • Può rompere codice esistente.

Simboli in package.json

Simbolo Significato Range
^4.18.0 Minor + patch >=4.18.0 <5.0.0
~4.18.0 Solo patch >=4.18.0 <4.19.0
4.18.0 Versione fissa Solo 4.18.0
  • ^4.18.0 → può installare 4.18.5 o 4.20.1, ma non 5.0.0.
  • ~4.18.0 → può installare 4.18.5, ma non 4.19.0.

5. NPM (Node Package Manager)

Package manager predefinito per progetti Node.js.

  • Gestisce dipendenze, versioni e script.
  • Registry online con milioni di pacchetti.
  • Installato automaticamente con Node.js.

File principali

  • package.json: metadati e dipendenze.
  • package-lock.json: versioni esatte installate.
  • node_modules/: cartella dei pacchetti.

Comandi comuni

# installa tutte le dipendenze npm install # installa un pacchetto npm install express # aggiorna i pacchetti npm update # rimuove un pacchetto npm uninstall express # esegue uno script npm run test

6. Promise in JavaScript

Rappresentano un valore disponibile in futuro.

Creazione

new Promise((resolve, reject) => { // operazione asincrona if (successo) { resolve(valore); } else { reject(errore); } });

Stati

  • pending: in attesa, result = undefined.
  • fulfilled: completata con successo → resolve(value).
  • rejected: errore → reject(error).

Metodi

Metodo Gestisce Quando Ritorna
then() resolve Solo successo Nuova Promise
catch() reject + errori Solo errore Nuova Promise
finally() Entrambi Sempre Promise originale
  • Una Promise settle una sola volta (fulfilled o rejected) e non cambia più.
  • catch() intercetta reject(), throw ed errori nei then().
  • finally() non modifica il risultato, è solo per cleanup.

7. async/await

Sintassi più leggibile per lavorare con Promise.

Funzioni async

async function ok() { return 1; // Promise.resolve(1) } async function error() { throw new Error("..."); // Promise.reject(...) }

await

async function caricaDati() { console.log("Inizio richiesta"); const response = await fetch(URL); console.log("Risposta ricevuta"); const data = await response.json(); console.log("Dati parsati"); return data; }
  • await si può usare solo dentro funzioni async.
  • Sospende la funzione, non il thread JS (event loop continua).
  • Se la Promise è rejected, viene generato un errore catturabile con try/catch.

async/await vs then/catch

  • async/await: codice più sequenziale, usa try/catch.
  • then/catch: catene di callback, evidenzia la natura asincrona.

8. fetch – richieste HTTP

Interfaccia moderna per richieste HTTP, basata su Promise.

Sintassi base

let response = fetch(URL, [options]);

Esempi metodi

// GET (default) fetch("https://api.example.com/users"); // POST fetch(URL, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ name: "Mario" }) }); // PATCH fetch("/corsi/8", { method: "PATCH", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ posti: 15 }) }); // DELETE fetch(URL, { method: "DELETE" });

PUT vs PATCH (aggiornamento)

  • PUT sostituisce completamente la risorsa → devi inviare tutti i campi.
  • PATCH modifica solo i campi indicati → ideale per update parziali.

Response object

const status = response.status; // es. 200, 404 const ok = response.ok; // true se 2xx if (!response.ok) { throw new Error(`HTTP error: ${response.status}`); } const text = await response.text(); const data = await response.json();
  • Il body è uno stream, i metodi text()/json() sono asincroni.
  • response.json() legge lo stream, ricostruisce il testo e fa il parsing JSON.

9. Error handling

Gestione degli errori con oggetto Error, try/catch e throw.

Oggetto Error

const err = new Error("messaggio"); console.log(err.message);
  • Proprietà principali: message, name, spesso stack.

try/catch e throw

try { if (qualcosaVaMale) { throw new Error("Errore generato manualmente"); } } catch (err) { console.error(err.message); }
  • throw interrompe il flusso normale e passa il controllo al catch più vicino.
  • In una Promise, un throw la rende rejected.

Errori comuni

Tipo Significato Esempio
TypeError Tipo sbagliato null.toString()
RangeError Valore fuori range new Array(-1)
ReferenceError Variabile mancante Uso di variabile non dichiarata
SyntaxError Sintassi errata JSON malformato
NetworkError Errore di rete fetch fallisce per connessione

10. Esempi completi REST API

Fetch con async/await e con then/catch.

10.1 async/await

async function getUsers() { try { const response = await fetch("https://api.example.com/users"); if (!response.ok) { throw new Error(`HTTP error: ${response.status}`); } const users = await response.json(); console.log("Utenti recuperati:", users); return users; } catch (err) { console.error("Errore nel recupero:", err.message); } finally { console.log("Richiesta conclusa"); } }

10.2 then/catch

fetch("https://api.example.com/users") .then(response => { if (!response.ok) { throw new Error(`HTTP error: ${response.status}`); } return response.json(); }) .then(users => { console.log("Utenti recuperati:", users); }) .catch(err => { console.error("Errore:", err.message); }) .finally(() => { console.log("Richiesta conclusa"); });

11. Node.js

Runtime per eseguire JavaScript lato server.

  • Non è un linguaggio, ma un ambiente basato su motore V8.
  • Supporta server HTTP e API REST.
  • Event-driven, non-blocking I/O, single-threaded con event loop.

11.1 server.listen()

const http = require('http'); const server = http.createServer((req, res) => { res.writeHead(200, { 'Content-Type': 'text/plain' }); res.end('Hello World'); }); server.listen(3000, () => { console.log("Server in ascolto sulla porta 3000"); });

11.2 Eventi data & end

let body = ''; req.on('data', chunk => { body += chunk.toString(); }); req.on('end', () => { const data = JSON.parse(body); console.log(data); });
  • data: chiamato più volte, ogni volta arriva un chunk.
  • end: chiamato una sola volta, quando il body è completo.
  • Fare JSON.parse in data rischia SyntaxError perché il JSON è incompleto.

12. Design REST – Best practices

URI con sostantivi, azioni nei metodi HTTP.

Endpoint problematico

DELETE /annulla?biglietto=12
  • Verbo nell’URI (/annulla).
  • ID passato come query.

Versione corretta

DELETE /biglietti/12
  • URI identifica la risorsa (/biglietti/12).
  • Metodo HTTP esprime l’azione (DELETE).

Regole d’oro URI REST

  • Sostantivi plurali: /users, /orders.
  • Gerarchia chiara: /users/5/orders/10.
  • Niente verbi: niente /getUsers.
  • ID nell’URI, non solo in query string.
  • Lowercase e trattini: /user-profiles.

13. cURL – testing API

Strumento da terminale per inviare richieste HTTP.

Flag principali

-X – metodo HTTP (es. -X POST).
-d – body della richiesta (es. JSON).
-H – header (es. Content-Type).
-i – mostra header di risposta.
-v – verbose/debug.
-O – salva output in file.
--retry N – ritenta N volte.
--retry-delay N – pausa tra tentativi.
--max-time N – timeout in secondi.

Esempi

# GET curl https://api.example.com/users # POST JSON curl -X POST https://api.example.com/users \ -H "Content-Type: application/json" \ -d '{"name":"Mario","email":"mario@example.com"}' # PUT curl -X PUT https://api.example.com/users/10 \ -H "Content-Type: application/json" \ -d '{"name":"Mario","email":"mario.new@example.com"}' # PATCH curl -X PATCH https://api.example.com/users/10 \ -H "Content-Type: application/json" \ -d '{"email":"mario.new@example.com"}' # DELETE curl -X DELETE https://api.example.com/users/10 # con header risposta curl -i https://api.example.com/users # retry + timeout curl --retry 3 --retry-delay 2 --max-time 10 https://api.example.com/users

14. Riepilogo lampo

Punti chiave da ricordare per la verifica.

  • REST è stateless, ogni richiesta è indipendente e auto-contenuta.
  • GET è safe e idempotente, POST non è idempotente e ha side effects.
  • PUT sostituisce tutto, PATCH modifica solo i campi indicati.
  • DELETE è idempotente: chiamarlo più volte ha lo stesso effetto finale.
  • Nesting risorse per relazioni gerarchiche (/artisti/3/concerti).
  • Status code: 2xx successo, 4xx errore client, 5xx errore server.
  • Content-Type è fondamentale per l’interpretazione del body.
  • SemVer: MAJOR.MINOR.PATCH, ^ accetta minor+patch, ~ solo patch.
  • Promise hanno 3 stati; then per successi, catch per errori, finally sempre.
  • async restituisce sempre una Promise, await sospende la funzione.
  • fetch è asincrono, response.json() legge uno stream.
  • fetch non fallisce automaticamente su 400/500: devi controllare response.ok.
  • Node.js usa eventi data e end perché il body arriva a pezzi.
  • URI REST: sostantivi plurali, niente verbi, ID nell’URI.
  • cURL è perfetto per testare rapidamente API da terminale.
